# Arc Ledger Match — инструкция

Инструмент помогает разобрать полученные USDC по уже существующим счетам.
Он полезен фрилансеру или небольшой команде, у которых счета живут в таблице,
а клиент платит несколькими переводами, переплачивает или оплачивает сразу два
счёта. На выходе видно распределённую сумму, остаток, переплату и основание
каждого решения. Это средство сверки локального списка, а не финансовый аудит
и не налоговое заключение.

## Установка и запуск

Нужны Node.js 20.19 или новее, npm, Git и современный браузер. Node.js 22
рекомендован для повторения CI. Кошелёк, USDC, ключи и аккаунт не нужны.

```sh
git clone https://github.com/kuilef/arc-ledger-match.git
cd arc-ledger-match
npm ci --ignore-scripts
npm run build
npm start
```

Откройте `http://127.0.0.1:5194`. Сервер доступен только на этом компьютере.
Если порт занят, выберите другой: в PowerShell `$env:PORT='5195'; npm start`,
в Linux/macOS `PORT=5195 npm start`. Чужой сервер останавливать не требуется.
После работы остановите свой сервер Ctrl+C. Пересборка после изменения кода:
`npm run build`. Команда `npm run dev` сначала собирает, затем запускает;
автоматического обновления исходников нет.

## Пройти демонстрацию

При открытии страницы сразу загружается синтетический набор. Интернет для него
не нужен: файлы подаёт локальный сервер. Все его платежи помечены как
`imported-unverified`; они не взяты из настоящих транзакций.

1. В таблице счетов найдите `INV-PAID`: 120 USDC распределены по импортированному
   указанию номера счёта. `INV-PARTIAL` получил 40 из 100. `INV-OVER` получил
   два наблюдения, 80 и 30; переплата составляет 10.
2. Платёж `demo-ambiguous` на 50 подходит двум счетам. Оба остаются `unpaid`.
   Даже единственный кандидат сам по себе не означает оплату.
3. `demo-split` на 100 распределён вручную: 60 на `INV-SPLIT-A` и 40 на
   `INV-SPLIT-B`. Разверните allocation evidence и посмотрите основания.
4. Выберите `demo-ambiguous`, счёт `INV-CANDIDATE-A`, сумму `25` и впишите
   причину. Нажмите Save allocation. Счёт станет частично распределённым.
5. Попробуйте направить ещё `26` на `INV-CANDIDATE-B`: программа отклонит
   перерасход. `25` допустимы. Сумма всех распределений одного платежа не
   превышает его principal.
6. Export report JSON сохраняет входные записи, выводы, основания и RPC
   observations. Invoice report CSV и Payment report CSV удобны для просмотра
   в таблице. Allocations JSON сохраняет ручные решения для точного повторного
   импорта. Allocations CSV предназначен для просмотра в таблице.

Load synthetic demo сбрасывает текущий набор. Clear ledger очищает память
страницы. Перед закрытием выгрузите нужные записи: автоматического сохранения
в браузерное хранилище или на сервер нет.

## Импорт собственных данных

Выберите Collection и Format, вставьте текст или выберите файл, затем нажмите
Import rows. Размер — до 2 MB, до 5 000 записей в коллекции. CSV — с заголовком,
JSON — массив объектов. Неверный импорт не меняет предыдущий список.
В отчёте допускается не более 5 000 candidate links суммарно. При превышении
лимита операция отклоняется целиком, текущие данные и RPC evidence сохраняются.
Уточните sender/receiver/период или разделите исходный набор на меньшие части.
Импорт счетов или платежей сбрасывает ручные распределения; сначала загрузите
обе коллекции, затем allocations. Импорт платежей также убирает старую RPC
коллекцию. Совершенно новый набор удобнее начать с Clear ledger.

Минимальный CSV счетов:

```csv
invoice_id,expected_amount
INV-2026-001,100.000001
INV-2026-002,60
```

Расширенный счёт может содержать `sender`, `receiver`, `start_at`, `end_at`.
Адрес — `0x` и 40 hex-символов. Дата — UTC, например `2026-10-08T00:00:00Z`.
Если указан период, платёж без даты не проходит автоматическое сопоставление.

Минимальный CSV наблюдаемых платежей:

```csv
payment_id,amount,invoice_id
bank-ledger-row-1,40,INV-2026-001
bank-ledger-row-2,60,
```

Необязательные поля: `sender`, `receiver`, `occurred_at`, `invoice_id`.
`invoice_id` здесь — ваше утверждение из исходного учёта. Если счёт существует
и его ограничения соблюдены, свободный остаток распределяется по этому
указанию. При расхождении будет предупреждение. RPC не добавляет такие номера.

Ручные решения:

```json
[
  {"invoice_id":"INV-2026-001","payment_id":"bank-ledger-row-2","amount":"30","reason":"Клиент подтвердил распределение в письме"},
  {"invoice_id":"INV-2026-002","payment_id":"bank-ledger-row-2","amount":"30","reason":"Вторая часть согласованного распределения"}
]
```

Все денежные значения в JSON должны быть строками: `"100.01"`. `100.01`,
`1e2`, отрицательные значения, ноль principal и более 18 знаков после точки
отклоняются. Значения считаются через bigint. В CSV десятичный разделитель —
точка. Поля с запятыми, кавычками и переносами заключайте в кавычки;
внутреннюю кавычку повторяйте.

Придумывайте стабильный `payment_id` для строки исходного учёта. Дубликат того
же ID отклоняется. Одна и та же операция под двумя разными IDs без общих
идентификаторов не распознаётся автоматически. Удалите такие дубликаты до
импорта; не добавляйте тот же перевод одновременно вручную и через RPC.
Префикс `arc:` зарезервирован для RPC. Подделать RPC provenance через JSON
импорт нельзя. Неизвестные поля отклоняются. CSV отчётов содержит дополнительные
поля и не является форматом входного списка. Для точного повторного импорта
ручных решений используйте Allocations JSON. CSV выгрузки предназначены для
табличного просмотра: защита от формул добавляет апостроф к строкам вроде
`-INV`, `+PAY` и `=reference`, поэтому ID после выгрузки может отличаться от
исходного. Импорт не снимает апостроф: он может быть частью настоящего ID.

## Проверить выбранные публичные транзакции

Укажите от одного до десяти публичных transaction hashes Arc mainnet в Observe
public transfers, выберите RPC и нажмите Read selected hashes. Проверяется chain
5042, успешный receipt, связь log с receipt и block. Only selected hashes,
chain check и необходимые block hashes уходят к провайдеру. Счета, суммы счетов,
их номера и причины распределения остаются в браузере.

Система берёт principal из native USDC system Transfer с 18 decimals.
ERC20-USDC log с 6 decimals может быть зеркалом той же операции и не увеличивает
сумму. Gas отдельно: `gasUsed × effectiveGasPrice`. Комиссия относится к
транзакции целиком; программа не разносит её по коммерческим счетам.

Даже успешный публичный перевод не доказывает оплату конкретного счёта.
Результат появится как кандидат или свободный платёж. Для коммерческой связи
нужны ваши документы и явное allocation с причиной.

RPC observations сохраняют провайдера, UTC-время, методы и исходные ответы.
Здесь видны null receipts, ошибки, неподдержанные события и отдельно gas fees.
Таймаут — 8 секунд на запрос, для временных ошибок не более одного повтора.
RPC redirects запрещены: выбранные hashes не пересылаются на другой origin
по перенаправлению провайдера.
Повторный успешный запрос не задваивает тот же log. RPC не даёт криптографической
проверки состояния и не заменяет независимую проверку провайдера.

При повторном чтении выбранный hash заменяет всю свою RPC-группу. Если receipt
стал недоступен или не поддерживается, прежний платёж исключается из текущего
списка, а зависевшие от него allocations снимаются с предупреждением. Если
principal уменьшился ниже уже распределённой суммы, его ручные распределения
тоже снимаются. Общий сбой до проверки chain оставляет прежний набор как
временную запись прошлых наблюдений и показывает ошибку. История ограничена
1 000 RPC-запросами на сессию; для длительной работы заранее выгружайте отчёт.

## Ограничения и безопасность

Только текущая схема mainnet. Testnet, исторические legacy events,
ERC20-only/mismatched события, mint/burn/self/zero events, удалённые logs и
некорректные данные не превращаются в оплату. Массового сканирования кошелька,
индексации истории, конвертации валют и onchain invoice references нет.

`paid` означает, что ожидаемая сумма покрыта распределениями этого локального
набора. Проверьте imported-unverified и explicit-user основания. Ручное
распределение может переопределить ограничения счёта; это отмечается предупреждением.
Подписи, отправка денег, хранение ключей и подключение кошелька отсутствуют.
Никаких CDN или трекеров. Экспорт с вашими счетами может содержать конфиденциальные
данные: не публикуйте его вместе с исходниками. В репозитории только синтетические
записи и публичные mainnet receipts. .env.example содержит только placeholders.

## Проверки

```sh
npm run lint
npm run typecheck
npm test
npm run test:ui
npm audit --audit-level=high
npm run smoke:rpc
```

test:ui использует установленный Chrome и собственный временный сервер.
Для Chromium: `npx --no-install playwright install chromium`, затем в PowerShell
`$env:PW_CHANNEL='chromium'; npm run test:ui` или `PW_CHANNEL=chromium npm run
test:ui` в Linux/macOS. Установка браузера для CI делается в отдельном runner.
smoke:rpc выполняет только несколько публичных чтений и обновляет
`evidence/live-mainnet.json`; ни одного onchain действия.
Фактически выполненные результаты приведены в `docs/VERIFICATION.md`.

Грант готовится отдельно по `GRANTS_RU.md`. Публикацию сайта, регистрацию,
подачу, подтверждение личности и кошелёк получателя выполняет сам пользователь.
